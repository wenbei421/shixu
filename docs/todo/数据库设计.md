## 1. 设计原则与取舍

### 1.1 十条设计原则

| # | 原则 | 理由 |
|---|---|---|
| 1 | **UUID v7 作为主键** | 时间有序，B-tree 索引友好，天然去中心化，未来同步无冲突 |
| 2 | **时间统一 UTC 毫秒** | 跨时区不丢数据，展示时再转本地 |
| 3 | **软删除 + Tombstone** | 为同步和撤销留后路，物理删除只在「清空回收站」时发生 |
| 4 | **HLC（混合逻辑时钟）** | 比单纯 Lamport 更精确，比 NTP 更可靠，同步冲突解决的基础 |
| 5 | **操作日志（oplog）** | 所有写操作入日志，用于同步、撤销、审计 |
| 6 | **Fractional Index 排序** | 手动排序只改一列，不触发全表重排 |
| 7 | **FTS5 全文搜索** | SQLite 原生，比 LIKE 快 10–100 倍 |
| 8 | **严格模式 STRICT 表** | SQLite 3.37+ 支持，类型安全，避免「字符串存进整数列」 |
| 9 | **部分索引（Partial Index）** | 只索引活跃数据，节省空间、提升写入 |
| 10 | **外键 + 触发器双保险** | 约束由 DB 保证，不依赖应用层 |

### 1.2 明确取舍

| 取舍 | 选择 | 放弃 |
|---|---|---|
| 同步复杂度 | HLC + oplog | CRDT（过重） |
| 重复任务 | 单表 + 懒生成实例 | 提前生成未来 N 次（浪费空间） |
| 项目嵌套 | 支持一层 `parent_id` | 无限嵌套（UI 复杂度爆炸） |
| 标签 | 多对多关联表 | JSON 数组（无法高效查询） |
| 附件 | 存路径 + 元数据，文件落盘 | 存 BLOB（DB 膨胀） |
| 全文搜索 | FTS5 虚拟表 | LIKE + 索引（慢） |

### 3.5 任务表（核心）

```sql
CREATE TABLE tasks (
  id             TEXT PRIMARY KEY,        -- UUID v7
  title          TEXT NOT NULL CHECK (length(title) > 0),
  description    TEXT NOT NULL DEFAULT '',

  -- 状态
  status         TEXT NOT NULL DEFAULT 'todo'
                 CHECK (status IN ('todo', 'doing', 'done', 'cancelled')),
  priority       TEXT NOT NULL DEFAULT 'none'
                 CHECK (priority IN ('high', 'medium', 'low', 'none')),

  -- 时间
  due_at         INTEGER,                 -- UTC 毫秒，可空
  due_timezone   TEXT,                    -- IANA 时区，如 'Asia/Shanghai'
  start_at       INTEGER,                 -- 开始时间（P1）
  completed_at   INTEGER,
  archived       INTEGER NOT NULL DEFAULT 0 CHECK (archived IN (0, 1)),

  -- 归属
  project_id     TEXT,
  parent_id      TEXT,                    -- 子任务（一级）

  -- 排序
  "order"        REAL NOT NULL DEFAULT 0,

  -- 重复（P1）
  recurrence_rule TEXT,                   -- RFC 5545 RRULE 字符串
  recurrence_end  INTEGER,                -- 重复结束时间
  recurrence_count INTEGER,               -- 重复次数

  -- 元数据
  source         TEXT NOT NULL DEFAULT 'manual'
                 CHECK (source IN ('manual', 'quick', 'import', 'api')),
  created_at     INTEGER NOT NULL,
  updated_at     INTEGER NOT NULL,
  deleted_at     INTEGER,
  hlc            TEXT NOT NULL,

  FOREIGN KEY (project_id) REFERENCES projects(id) ON DELETE SET NULL,
  FOREIGN KEY (parent_id)  REFERENCES tasks(id)    ON DELETE CASCADE
) STRICT;

-- 核心索引
CREATE INDEX idx_tasks_status_due
  ON tasks(status, due_at)
  WHERE deleted_at IS NULL AND archived = 0;

CREATE INDEX idx_tasks_project
  ON tasks(project_id, "order")
  WHERE deleted_at IS NULL AND archived = 0;

CREATE INDEX idx_tasks_parent
  ON tasks(parent_id, "order")
  WHERE deleted_at IS NULL;

CREATE INDEX idx_tasks_due
  ON tasks(due_at)
  WHERE deleted_at IS NULL AND archived = 0 AND status != 'done';

CREATE INDEX idx_tasks_archived
  ON tasks(archived, updated_at DESC)
  WHERE deleted_at IS NULL;

CREATE INDEX idx_tasks_completed
  ON tasks(completed_at DESC)
  WHERE deleted_at IS NULL AND status = 'done';

-- 同步用
CREATE INDEX idx_tasks_hlc ON tasks(hlc) WHERE deleted_at IS NULL;
CREATE INDEX idx_tasks_updated ON tasks(updated_at DESC);
```

### 3.13 全文搜索（FTS5）

```sql
-- 内容索引
CREATE VIRTUAL TABLE tasks_fts USING fts5(
  title,
  description,
  content='tasks',
  content_rowid='rowid',
  tokenize='unicode61 remove_diacritics 2'
);

-- 同步触发器：INSERT
CREATE TRIGGER tasks_fts_insert AFTER INSERT ON tasks
WHEN NEW.deleted_at IS NULL
BEGIN
  INSERT INTO tasks_fts(rowid, title, description)
  VALUES (NEW.rowid, NEW.title, NEW.description);
END;

-- 同步触发器：UPDATE
CREATE TRIGGER tasks_fts_update AFTER UPDATE ON tasks
BEGIN
  INSERT INTO tasks_fts(tasks_fts, rowid, title, description)
  VALUES ('delete', OLD.rowid, OLD.title, OLD.description);
  INSERT INTO tasks_fts(rowid, title, description)
  SELECT NEW.rowid, NEW.title, NEW.description
  WHERE NEW.deleted_at IS NULL;
END;

-- 同步触发器：DELETE
CREATE TRIGGER tasks_fts_delete AFTER DELETE ON tasks
BEGIN
  INSERT INTO tasks_fts(tasks_fts, rowid, title, description)
  VALUES ('delete', OLD.rowid, OLD.title, OLD.description);
END;
```

## 4. 关键设计决策

### 4.1 为什么用 UUID v7 而不是 v4？

| 维度 | UUID v4 | UUID v7 | 自增 INTEGER |
|---|---|---|---|
| 随机性 | 完全随机 | 时间前缀 + 随机 | 完全有序 |
| B-tree 插入 | 随机写，页分裂多 | 顺序写，性能好 | 顺序写 |
| 分布式生成 | ✅ | ✅ | ❌ |
| 信息泄露 | 无 | 泄露生成时间 | 泄露总量 |
| 长度 | 36 字符 | 36 字符 | 8 字节 |

**结论**：v7 兼顾了分布式生成和顺序写入，是本地优先应用的最优解。

### 4.2 为什么用 HLC 而不是 Lamport / 物理时钟？

- **物理时钟**：设备间可能偏差几秒，同步时无法判断先后
- **Lamport**：只有逻辑顺序，丢失真实时间信息，UI 展示困难
- **HLC**：`{物理时间, 逻辑计数}` 二元组，既保证因果顺序，又接近真实时间

```
HLC 格式：{wall_ms}-{counter}-{device_id}
示例：1726550400000-0001-a1b2c3d4

比较规则：
1. 先比 wall_ms
2. 相同则比 counter
3. 再相同比 device_id（打破平局）
```

### 4.3 为什么用 Fractional Index 排序？

传统 `position INTEGER` 排序，插入时需更新后续所有行：

```sql
-- 慢：插入到第 5 位，要更新第 5 位之后所有行
UPDATE tasks SET position = position + 1 WHERE position >= 5;
```

Fractional Index 只改一列：

```
初始：  a=1.0, b=2.0, c=3.0
插入到 a 和 b 之间：a=1.0, new=1.5, b=2.0
再插入：a=1.0, new1=1.25, new2=1.5, b=2.0
```

**推荐实现**：使用 `fractional-indexing` 库（字符串版本，比浮点更抗精度耗尽）。

### 4.4 为什么用 STRICT 表？

```sql
-- 非 STRICT 表：SQLite 会做隐式类型转换，容易出 bug
CREATE TABLE t (id INTEGER);
INSERT INTO t VALUES ('hello');  -- 成功！存进去是 'hello'

-- STRICT 表：类型严格
CREATE TABLE t (id INTEGER) STRICT;
INSERT INTO t VALUES ('hello');  -- 报错：cannot store TEXT value in INTEGER column
```

**代价**：不支持 `ANY` 类型、不支持 `BLOB` 以外的无类型列。  
**收益**：类型安全，避免「字符串存进日期列」这类经典 bug。

### 4.5 为什么保留 `subtasks` 表又推荐 `parent_id`？

| 方案 | 优点 | 缺点 | 适用 |
|---|---|---|---|
| A. `tasks.parent_id` 自引用 | 无限嵌套、统一查询、复用所有字段 | 查询要递归 | 推荐 |
| B. 独立 `subtasks` 表 | 简单、子任务字段少 | 无法嵌套、字段重复 | 轻量场景 |

**推荐**：MVP 用方案 A，`parent_id` 为空表示顶层任务。查询时用 `WITH RECURSIVE` 或应用层组装。

```sql
-- 递归查询某任务的所有子孙
WITH RECURSIVE tree AS (
  SELECT * FROM tasks WHERE id = ?
  UNION ALL
  SELECT t.* FROM tasks t JOIN tree ON t.parent_id = tree.id
  WHERE t.deleted_at IS NULL
)
SELECT * FROM tree ORDER BY "order";
```

### 4.6 为什么时间存 UTC 毫秒而不是 ISO 字符串？

| 维度 | INTEGER（UTC ms） | TEXT（ISO 8601） |
|---|---|---|
| 存储 | 8 字节 | 20–30 字节 |
| 比较 | 整数比较，极快 | 字符串比较，慢 |
| 索引 | B-tree 友好 | 一般 |
| 时区 | 需转换 | 自带时区 |
| 可读性 | 差 | 好 |

**结论**：存 UTC 毫秒，展示时用 `Intl.DateTimeFormat` 转本地。  
**例外**：`due_timezone` 单独存 IANA 时区，用于重复任务（跨 DST 时正确）。

### 4.7 为什么用软删除？

```sql
-- 软删除：UPDATE tasks SET deleted_at = ? WHERE id = ?
-- 硬删除：DELETE FROM tasks WHERE id = ?
```

| 场景 | 软删除 | 硬删除 |
|---|---|---|
| 同步冲突 | ✅ 可对比 | ❌ 丢失 |
| 撤销删除 | ✅ 可恢复 | ❌ 不可 |
| 空间占用 | 略大 | 小 |
| 查询复杂度 | 需 `WHERE deleted_at IS NULL` | 无 |

**结论**：软删除 + 定期清理（30 天前自动物理删除）。

## 5. 索引策略

### 5.1 索引设计原则

1. **只索引会用于 WHERE / ORDER BY / JOIN 的列**
2. **复合索引遵循最左前缀原则**
3. **高频查询用覆盖索引**（`INCLUDE` 模拟：把 SELECT 列加进索引）
4. **部分索引减少体积**：`WHERE deleted_at IS NULL`
5. **避免过度索引**：每个索引都拖慢写入

### 5.2 核心查询与对应索引

| 查询场景 | 索引 | 类型 |
|---|---|---|
| 收集箱（无日期未完成） | `idx_tasks_status_due` | 部分 |
| 今天（due < 明天0点） | `idx_tasks_due` | 部分 |
| 即将到来（未来 7 天） | `idx_tasks_due` | 部分 |
| 按项目列任务 | `idx_tasks_project` | 部分 |
| 按标签列任务 | `idx_task_tags_tag` | 普通 |
| 已完成列表 | `idx_tasks_completed` | 部分 |
| 归档列表 | `idx_tasks_archived` | 部分 |
| 子任务 | `idx_tasks_parent` | 部分 |
| 待触发提醒 | `idx_reminders_pending` | 部分 |
| 未同步操作 | `idx_op_log_unsynced` | 部分 |
| 全文搜索 | `tasks_fts` | FTS5 |

### 5.3 索引大小估算（10 万任务）

| 索引 | 预计大小 |
|---|---|

## 7. 触发器与数据完整性

### 7.1 自动维护 `updated_at`

```sql
CREATE TRIGGER tasks_updated_at
AFTER UPDATE ON tasks
FOR EACH ROW
WHEN NEW.updated_at = OLD.updated_at
BEGIN
  UPDATE tasks SET updated_at = CAST(strftime('%s', 'now') AS INTEGER) * 1000
  WHERE id = NEW.id;
END;
```

**注意**：更推荐在应用层设置 `updated_at`，因为 SQLite 的 `strftime` 精度只到秒，且触发器会额外消耗性能。

### 7.2 自动维护标签使用计数

```sql
-- 增加
CREATE TRIGGER task_tags_insert
AFTER INSERT ON task_tags
FOR EACH ROW
BEGIN
  UPDATE tags SET usage_count = usage_count + 1 WHERE id = NEW.tag_id;
END;

-- 减少
CREATE TRIGGER task_tags_delete
AFTER DELETE ON task_tags
FOR EACH ROW
BEGIN
  UPDATE tags SET usage_count = usage_count - 1 WHERE id = OLD.tag_id;
END;
```

### 7.3 自动记录任务日志

```sql
CREATE TRIGGER tasks_log_update
AFTER UPDATE ON tasks
FOR EACH ROW
WHEN NEW.deleted_at IS OLD.deleted_at
BEGIN
  INSERT INTO task_logs (id, task_id, action, field, old_value, new_value, created_at)
  VALUES (
    lower(hex(randomblob(16))),
    NEW.id,
    CASE
      WHEN NEW.status = 'done' AND OLD.status != 'done' THEN 'complete'
      WHEN NEW.status != 'done' AND OLD.status = 'done' THEN 'uncomplete'
      WHEN NEW.archived = 1 AND OLD.archived = 0 THEN 'archive'
      WHEN NEW.archived = 0 AND OLD.archived = 1 THEN 'unarchive'
      ELSE 'update'
    END,
    NULL,
    NULL,
    NULL,
    CAST(strftime('%s', 'now') AS INTEGER) * 1000
  );
END;
```

### 8.3 Rust 侧迁移执行

```rust
pub fn run_migrations(conn: &Connection) -> Result<()> {
    let current: i32 = conn
        .query_row("SELECT COALESCE(MAX(version), 0) FROM schema_version", [], |r| r.get(0))
        .unwrap_or(0);

    let migrations = [
        (1, include_str!("../migrations/001_initial.sql")),
        (2, include_str!("../migrations/002_add_recurrence.sql")),
        // ...
    ];

    for (version, sql) in migrations {
        if version > current {
            conn.execute_batch(sql)?;
            log::info!("Applied migration {}", version);
        }
    }
    Ok(())
}
```

### 9.2 备份实现

```rust
pub fn backup(db_path: &Path, backup_dir: &Path) -> Result<PathBuf> {
    let timestamp = chrono::Local::now().format("%Y%m%d_%H%M%S");
    let backup_path = backup_dir.join(format!("shixu_{}.db", timestamp));

    let conn = Connection::open(db_path)?;
    // VACUUM INTO 是 SQLite 官方推荐的备份方式，原子、一致
    conn.execute(
        &format!("VACUUM INTO '{}'", backup_path.display()),
        [],
    )?;

    Ok(backup_path)
}
```

    Ok(())

## 12. 反模式与避免事项

### 12.1 常见反模式

| 反模式 | 问题 | 正确做法 |
|---|---|---|
| 用 TEXT 存日期 | 比较慢、排序错 | INTEGER UTC 毫秒 |
| 用逗号分隔存标签 | 无法索引、无法 JOIN | 关联表 |
| `SELECT *` | 浪费 IO、易出错 | 明确列名 |
| 在 WHERE 里用函数 | 索引失效 | 把函数移到应用层 |
| 过度索引 | 写入慢 | 只索引必要列 |
| 无 LIMIT 的查询 | 大表可能 OOM | 始终 LIMIT |
| 无事务的批量写 | 慢 10 倍 | `BEGIN ... COMMIT` |
| 用 `INTEGER` 存布尔 | 语义不清 | `CHECK (x IN (0,1))` |
| 不用外键 | 数据不一致 | `PRAGMA foreign_keys = ON` |
| 迁移不可逆 | 升级后无法降级 | 只加不减 |

### 12.2 SQLite 特有的坑

| 坑 | 说明 | 规避 |
|---|---|---|
| 默认不开外键 | 需每次连接执行 PRAGMA | 连接初始化时执行 |
| 动态类型 | `INTEGER` 列可存字符串 | 用 STRICT 表 |
| `AUTOINCREMENT` 慢 | 维护 sqlite_sequence | 用 UUID |
| `DELETE` 不释放空间 | 需 VACUUM | 定期 `PRAGMA incremental_vacuum` |
| WAL 文件增长 | checkpoint 不及时 | 定期 `PRAGMA wal_checkpoint(TRUNCATE)` |
| `LIKE` 大小写 | 默认不区分 ASCII | 用 `COLLATE NOCASE` 或 FTS5 |
| 时间函数精度 | `strftime` 只到秒 | 应用层生成毫秒 |

### 12.3 数据一致性检查脚本

```sql
-- 检查孤立子任务（父任务不存在）
SELECT s.id FROM subtasks s
LEFT JOIN tasks t ON t.id = s.task_id
WHERE t.id IS NULL;

-- 检查孤立标签关联
SELECT tt.task_id FROM task_tags tt
LEFT JOIN tasks t ON t.id = tt.task_id
WHERE t.id IS NULL;

-- 检查完成态但无完成时间
SELECT id FROM tasks
WHERE status = 'done' AND completed_at IS NULL;

-- 检查标签计数不一致
SELECT g.id, g.usage_count, COUNT(tt.task_id) AS actual
FROM tags g
LEFT JOIN task_tags tt ON tt.tag_id = g.id
GROUP BY g.id
HAVING g.usage_count != actual;
```
